# UI 美观与交互体验优化开发计划

## 决策状态

- 状态：近期实施，按“基线 → 单流程试点 → 推广”推进。
- Rust：不进入近期计划；不安排 PoC、试点或迁移，不引入 Rust、N-API 或 WASM 依赖，不改变构建与发布矩阵。
- 技术路线：先进行必要的 TypeScript 结构、算法、数据流和现有工具链优化；只有测量证明仍有未满足的目标，才重新评估其他实现技术。
- UI 范围：VS Code 原生控件、浏览器扩展 popup、注入页面 overlay/modal。各 surface 的宿主约束不同，不做一次性全量视觉重做，不引入 React、Vue 或大型组件库。
- VS Code 面遵循宿主主题，不强行统一其主题和原生控件。

## 目标

1. 建立核心用户路径的任务效率、键盘可用性、对比度、反馈延迟和性能基线。
2. 选择一个审批弹窗或 popup 流程，以 CSS 变量和设计令牌完成小范围试点。
3. 通过体验、性能、可访问性及回滚检查后，再决定是否推广到其他 surface。

目标用户、优先用户路径、样本规模、团队容量和具体性能回退阈值尚未提供，均为**待确认**。不得将未经测量的数据写成当前表现或收益。

## 不在本期范围

- 全量 Rust 重写或将 Rust/N-API/WASM 引入近期生产构建。
- 全量 UI 重做、一次性替换所有浏览器和 VS Code 控件。
- 引入 React、Vue 或大型组件库。
- 强行重设 VS Code 宿主主题。
- 在没有用户授权的情况下启动交互式浏览器 QA。

## 实施阶段

| 阶段 | 工作项 | 交付物 | 负责人角色 | 退出条件 |
| ------ | ------ | ------ | ------------ | ---------- |
| 0. 范围确认 | 确认目标用户、核心任务、目标浏览器/VS Code 版本、测量和数据政策、团队负责人；确定回退阈值。 | 范围与指标确认记录 | 产品/项目负责人、UI 负责人、QA | 未知项已确认，或明确记为不阻塞的假设。 |
| 1. 基线 | 对连接/断连、初始化、审批/拒绝、查看结果与错误恢复中的优先路径采集效率、键盘、焦点、对比度和反馈延迟证据。 | 核心路径基线、a11y 检查结果、问题清单 | UI/TS 开发者、QA、a11y reviewer | 选定试点流程；关键指标可复测。 |
| 2. 单流程试点 | 在一个 popup 或审批弹窗流程引入语义化 CSS 变量；维持现有技术栈、协议和审批语义。 | 可回退的试点实现、测试、基线对比 | 对应 surface 的 TS 开发者、UI reviewer | 所有硬性 a11y 门槛通过；性能回退在事先约定范围内。 |
| 3. 试点验收 | 复测核心任务、键盘路径、屏幕阅读器、对比度、反馈延迟、布局和错误恢复；处理缺陷。 | 试点验收记录、缺陷与剩余风险 | QA、a11y reviewer、UI 负责人 | 负责人作出推广、再迭代或回滚决定。 |
| 4. 分步推广 | 按 surface 逐一推广经过验证的令牌与模式；保留宿主主题和 surface 差异。 | 分批 PR、测试证据、更新后的设计令牌说明 | 各 surface 维护者 | 每个 surface 单独通过检查，无整体切换要求。 |

团队规模和可用时间未知，当前不承诺日历日期或人日。每阶段由负责人根据实际人力拆分任务和排期。

## 基线与度量

每项数据记录环境、版本、操作步骤、样本量和测量方法；无数据时标为“待测”。优先记录：

- **任务效率：** 完成率、耗时（至少 p50；样本足够时报告 p95）、点击/输入次数、误操作和恢复次数。
- **键盘与可访问性：** 核心流程是否能仅用键盘完成；焦点顺序、可见焦点、弹窗焦点进入/退出；控件名称和状态是否能被屏幕阅读器识别。
- **视觉可读性：** 文本与控件对比度、缩放/窄视口下溢出、状态是否只依赖颜色传达。
- **交互与性能：** 从操作触发到可见反馈的延迟、UI 主线程长任务、popup 首次状态呈现时间；固定浏览器、设备和构建版本做前后对照。

若没有遥测许可，优先使用本地脚本化测试和经用户同意的可用性观察；不得记录对话内容、文件路径、命令参数或工具载荷来代替无障碍/性能指标。采集政策待确认。

## 设计与实现约束

- 令牌使用语义命名，至少覆盖颜色/状态、间距、字号、焦点样式和动效偏好；不通过单一颜色传递连接、审批或错误状态。
- 先复用原生 HTML 控件与现有 VS Code API；抽象只在多个 surface 确实共享且不会掩盖宿主差异时增加。
- 页面注入 UI 应继续考虑 Shadow DOM/宿主页面隔离、窄视口、长文本、缩放、焦点管理和 reduced-motion。
- 不改变安全审批语义、自动发送行为、桥接协议或用户数据处理方式；若需要改变，拆分为独立设计和审查。
- TypeScript 代码遵循仓库严格类型、ESLint 和跨包公共入口约定；相关浏览器与扩展测试放在所属包。

## 验收标准

以下为硬门槛：

- 核心用户流程可以仅用键盘完成；焦点顺序合理且焦点可见。
- 适用文本和控件满足 WCAG 2.2 AA 对比度要求；使用工具或人工记录测量结果。
- 严重级可访问性问题为 0；阻断级问题需修复或由负责人书面接受风险后才能继续。
- 交互反馈、布局、错误和审批状态在试点流程中有自动化或可复现的验收证据。
- 性能不得超过试点前批准的回退阈值。具体百分比/绝对值当前**待确认**，不得默认沿用未批准的建议值。
- 试点能独立回退，不依赖全量样式或组件迁移。

推荐量化但尚待基线确认的效率指标：核心任务完成率、p50 用时、点击/输入次数和错误恢复次数。没有基线前不设虚构目标值。

## 测试与发布

- 常规门禁按改动范围运行：`pnpm lint`、`pnpm test`；VS Code 集成受影响时运行 `pnpm test:extension`。
- 浏览器 bridge、popup 或注入 overlay 改动应运行相关包测试；必要时运行 `pnpm test:e2e:minimal`。该确定性 E2E 不等同于真实 UI 交互验收。
- 交互式 QA 只在用户明确授权后运行，且必须使用 `qa:start` 创建的隔离工作区与配置；遵循 [webcode-browser-qa Skill](../../.codex/skills/webcode-browser-qa/SKILL.md)。
- PR 记录受影响的 surface、测试结果、键盘/a11y 检查、对比基线和未覆盖风险。不得把未运行的检查描述为通过。

## 风险与回滚

| 风险 | 缓解 | 回滚条件 |
| ------ | ------ | ---------- |
| 视觉 token 影响页面宿主或 VS Code 主题 | 按 surface 试点；隔离注入样式；VS Code 控件遵循宿主主题。 | 宿主页面样式泄漏、主题适配明显退化或关键控件不可读。 |
| 动效或布局降低可访问性 | reduced-motion、键盘、屏幕阅读器和对比度检查作为门禁。 | 硬性 a11y 门槛未通过。 |
| 交互更新降低任务效率或响应性 | 与同环境基线对照，并记录回退阈值。 | 超出批准的性能/效率回退阈值。 |
| 试点推广后难以整体撤销 | 令牌与组件改动分批提交；避免不必要的跨 surface 抽象。 | 可独立 revert 对应试点或 surface PR。 |
| 缺少用户或遥测数据 | 先采用本地复现和明确授权的观察；数据不足即标记待确认。 | 不能证明需求或收益时暂停推广。 |

## Rust 方向性附录

Rust 不属于本期工作。只有满足下列任一触发条件，且团队具备 FFI 审查、调试和生产故障兜底能力时，才重新评估：

1. 可复现的端到端瓶颈被定位到语言运行时或计算核心；
2. 有明确的内存安全或 Node/浏览器逻辑复用需求；
3. 经测量确认，现有 TypeScript/子进程方案无法达到已批准目标。

重新评估时须比较全量重写、热点模块 Rust、FFI/N-API/WASM 局部集成和服务端/CLI 替换；提交可重复基准、威胁模型、跨平台打包成本、团队审查能力和回滚方案。AI 辅助编码不降低审查、调试和故障定位要求。
