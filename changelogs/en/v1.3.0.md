# v1.3.0 (2026-10-21)

## Features

- Added the unified `webcodeGateway.timeouts` settings: `commandExecutionMs`, `toolCallMs`,
  `bridgeCodeTtlMs`, `approvalTtlMs`, `browserLaunchWaitMs`, and `bridgeRequestMs` are all
  configurable, clamped to documented ranges, and applied by an automatic gateway restart.
  Startup now logs one `timeouts:` line with every resolved deadline, so you no longer have to
  guess whether a setting was picked up.
- Pairing can start from the browser side: the bridge popup discovers local workspace gateways
  (probing 34567-34576) and asks VS Code for confirmation before a single-use launch code is
  issued. The gateway gained two deliberately narrow unauthenticated routes — `GET /v1/ping`
  (no secrets) and `POST /v1/session/request` (JSON only, origin allowlist, rate window, and an
  explicit modal approval, all four required).
- Configuration changes are now classified: tooling keys (`servers`, `skillDirectories`,
  `commandShell.path`, `command.allowedRoots`, `timeouts`) hot-reload while keeping the bridge
  session; connection-identity keys (`port`, `idleTimeoutMinutes`, `aiSites`, `browser`) still
  cold-restart and revoke it.
- Gateway logs are persisted to `globalStorage/three-water666.gateway-vscode/logs/gateway-YYYYMMDD.log`
  (daily rotation, 7 days retained), including startup, stop, idle auto-stop, failed starts, and
  uncaught extension-host errors.
- Builds are self-identifying: activation writes a fingerprint line
  `build: version=… buildHash=… builtAt=… bridgeProtocol=… node=… vscode=…`, and the authenticated
  `GET /v1/status` also returns `version`, `buildHash`, `bridgeProtocolVersion`, and `startedAt`.
- The MCP client handshake now reports the real extension version instead of a hard-coded `1.0.0`.

## Upgrade notes (required reading)

1. **The browser bridge must match the VS Code extension version.** The handshake requires
   `VS Code extension version === browser extension version`; a mismatch is rejected outright.
2. **Restart the browser once after upgrading.** The new bridge build is staged first. If an
   isolated browser is running, the next connect warns that the browser must restart, then closes
   and relaunches it so the new bridge is loaded. Manual installs should run `pnpm bridge:sync`
   and then click the reload button on the bridge card in `chrome://extensions`.
3. **Reconnect once after upgrading.** The bridge session token lives in gateway memory, so an
   extension upgrade or restart invalidates it. Start the connection again from the VS Code status
   bar and pair once more. Automatic resume is planned for a later release.
4. Rollback: the previous vsix is kept in `release-archive/`; run
   `code --install-extension <old vsix> --force` to go back.

## Fixes

- Fixed the long-standing version drift between the browser bridge and the VS Code extension that
  produced "versions do not match" errors right after a fresh install.
- Fixed packaged artifacts having no build identity, which made "is the installed vsix the current
  code?" unanswerable. A release guard test now fails the build when the three manifests disagree.

## Restart continuity (automatic resume after a window reload)

- The gateway session token is now persisted per workspace: VS Code SecretStorage first (OS-encrypted,
  revocable per workspace), then a machine-secret-derived token, then an in-memory token with a log
  warning. After a window reload, extension restart, or gateway restart, a connected tab resumes with
  the same token and does not need to pair again.
- `GET /v1/status` gained `gatewayInstanceId` (new on every start) and `lastInterrupted` (how many
  calls were cut off and when). The redemption payload also carries `gatewayInstanceId`, so the
  browser can tell "the gateway restarted but the token is still valid" from "the token was rejected".
- Browser side: a 401 is retried once before the session is expired; returning to a tab probes
  immediately instead of waiting for the 60-second check; the disconnect notice now says recovery is
  in progress while keeping the reconnect hint.
- New `deactivate()` teardown (roughly a 300 ms hard budget, fully synchronous): reject new requests
  with 503, write the in-flight calls to
  `globalStorage/three-water666.gateway-vscode/state/shutdown-<workspaceId>.json`, then stop the
  gateway in `fast` mode while preserving the session token.
- Interrupted calls are reported, never replayed: the snapshot stores the tool name, start time, an
  argument digest (sha256) and a redacted preview capped at 120 characters, is limited to 16 KB, and
  expires after 10 minutes. The next start surfaces "retry them" in the log and in `lastInterrupted`.
- The security boundary is unchanged: the gateway still binds `127.0.0.1` only, and redemption still
  checks the origin allowlist, the protocol version, and a single-use launch code. Invalidating every
  connected tab requires rotating the token (API shipped in this release).
