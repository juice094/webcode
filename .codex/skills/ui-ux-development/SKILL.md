# webcode UI/UX 开发

开始任何 UI 相关实现前，先阅读 [UI 开发计划](../../../doc/plans/UI_UX_DEVELOPMENT_PLAN.md)，并按以下流程执行。

## 工作流

1. **确认 surface 和路径。** 明确改动属于 VS Code 原生控件、浏览器 popup 还是注入 overlay/modal；列出受影响的核心任务、宿主主题、键盘与屏幕阅读器需求。信息缺失时标记“待确认”，不要假设用户痛点或使用数据。
2. **先建基线。** 记录可复现步骤、完成率/耗时/点击输入数（若可采集）、焦点路径、对比度和反馈延迟。注明环境、版本、样本量和方法；没有基线就不得声称改善或性能回归。
3. **限定单流程改动。** 首选现有 HTML、TypeScript、VS Code API 和 CSS 变量/语义令牌；不引入 React、Vue、大型组件库、Rust/N-API/WASM，不做全量重写。VS Code UI 遵循宿主主题。不要顺手更改审批、安全、桥接协议或自动发送语义。
4. **把可访问性作为硬门槛。** 核心流程必须可键盘完成，焦点清晰可见，文本/控件满足 WCAG 2.2 AA 对比度，严重级 a11y 问题为 0。弹窗应检查焦点进入、退出与恢复；动效尊重 `prefers-reduced-motion`。
5. **比较性能。** 用相同环境对照基线与变更，测量反馈延迟、UI 长任务和相关首屏/状态呈现时间。性能回退阈值须在试点前由负责人批准；阈值未给出时标记待确认，不得擅自用某个百分比代替。
6. **运行范围适当的验证。** 运行相关单元测试、`pnpm lint`，以及受影响的包构建/测试；浏览器流程按需要运行 `pnpm test:e2e:minimal`。确定性 E2E 不代表真实 UI 已验收。
7. **交互式 QA 需要授权。** 不因收到实现请求就启动浏览器。只有用户明确授权后，才能按 `webcode-browser-qa` Skill 使用 `qa:start` 创建的隔离工作区/配置；完成后运行 `qa:stop`。
8. **提交证据与回滚。** 汇报改动 surface、测量方法与结果、a11y 检查、测试、未覆盖风险和回滚方式。试点应可独立 revert；未验证的内容写明“未验证”。

## Rust 决策边界

Rust 不进入近期 UI 计划，不安排 PoC/试点，不改变构建或发布矩阵。只有 UI 计划附录列出的触发条件成立后，才可提出重新评估；必须由具备互操作审查和生产兜底能力的负责人批准。AI 辅助开发不替代最终审查、调试与故障定位。

## 完成条件

- 变更限于获批的单流程或阶段范围。
- 硬性键盘、焦点、WCAG 2.2 AA 对比度与严重问题门槛通过。
- 性能未超过试点前已批准的回退阈值；没有阈值时不得宣称性能验收通过。
- 有对应测试和可执行回滚；测试或交互流程未运行时明确披露。
